# AJW Africa BDS Platform — Legal, Privacy and Accessibility Compliance Prompt

You are working on the **AJW Africa Business Development Services (BDS) Platform**, a Flutter app (Android + Web targets) backed by Supabase (Postgres database, Authentication, Storage, Row Level Security (RLS), Realtime and Edge Functions), with Google integrations (Meet, Calendar, Drive, Docs, Gmail).

User roles: **admin**, **owner** (enterprise/business owner), and **consultants** (accountant, marketing, legal).

The platform operates in Kenya, so the governing privacy law is **Kenya's Data Protection Act, 2019 (DPA)**, enforced by the **Office of the Data Protection Commissioner (ODPC)**. Use it as the baseline for every privacy item below.

## How to work

1. **Audit first, then build.** Before changing anything, review the codebase and produce a short compliance audit: for each item below, state what already exists, what is missing, and what you plan to do. Some items (privacy notice, data deletion, consent) may already be partly built from an earlier update — extend those rather than duplicating them.
2. Database changes go in **new Supabase migration files** only.
3. Never put secret keys in the Flutter app.
4. Legal pages are **drafts for a lawyer to review**. Use clearly marked placeholders like `[AJW REGISTERED NAME]`, `[PHYSICAL ADDRESS]`, `[CONTACT EMAIL]`, `[DATA PROTECTION OFFICER CONTACT]`, `[EFFECTIVE DATE]` for anything you cannot know, and list every placeholder in your final report.
5. Store legal page content in one editable place (e.g. a `legal/` folder of Markdown files or a Supabase table) so text can be updated without code changes, with a version number and "Last updated" date on each.
6. After each group of items, run `flutter analyze` and a build, fix errors, and report what changed and which files were touched.
7. **Wording rule for all user-facing text:** never use an acronym or abbreviation without spelling it out first; on first use, write the full term followed by the abbreviation in brackets.

## 0. Security documentation (do this first)

Create five security reference documents in a `docs/security/` folder. They are the rules every future change to this app (by me or by an Artificial Intelligence (AI) coding assistant) must follow. **This step does not change how the app works.** Write each document from what the code actually does, then add the rules it should follow. The only code changes allowed in this step are fixes where the current app contradicts these documents (see "Fixing contradictions" below).

1. **`SECURITY.md`** — the security rules for anyone (including AI assistants) writing code in this project:
   - How to handle user input: validate and sanitise everything on the server side (Edge Functions, database constraints, RLS), never trust the client; parameterised queries only; file upload type and size limits.
   - Secrets: passwords, Application Programming Interface (API) keys, the Supabase service role key and Google client secrets must never be in the Flutter code, the repository or logs. Where secrets live (environment variables / Supabase secrets), what is safe in the client (the Supabase anon key only, protected by RLS), and what to do if a secret leaks (rotate immediately).
   - Rules for dependencies, error messages (no stack traces or internal details shown to users), logging (no passwords, tokens or document contents in logs) and code review.
   - A short "Rules for AI assistants" section to follow on every task.

2. **`AUTH.md`** — how authentication and authorisation work:
   - How users sign up and log in (Supabase Authentication methods in use, Google sign-in if used), password rules, Multi-Factor Authentication (MFA) requirements per role.
   - Session handling: how long users stay signed in, token refresh, inactivity timeout, logout behaviour, what happens on password change.
   - Roles (admin, owner, accountant, marketing, legal) and a **permission matrix**: for every table, storage bucket, screen and Edge Function, what each role can view, create, edit and delete — and how each rule is enforced (RLS policy name, function check).
   - How Google OAuth (Open Authorisation) tokens are stored and refreshed, and which scopes are requested and why.

3. **`DATA_SECURITY.md`** — what sensitive data the app holds and how it is protected:
   - A data inventory: every type of personal and sensitive data (identity details, contact details, licences, certificates, financial records, meeting notes, emails, chat messages), where it is stored (table / bucket / Google), who can access it, and its sensitivity level.
   - Protection rules: encryption in transit and at rest, private buckets with short-lived signed links, access logging.
   - Retention and deletion: how long each data type is kept, when and how it is deleted or anonymised, and how data deletion requests are carried out.
   - Third parties that receive data (Supabase, Google, others found in the SDK audit), where their servers are, and the cross-border transfer basis under the Kenya Data Protection Act.
   - Breach response: who does what, and the 72-hour notification to the ODPC.

4. **`THREAT_MODEL.md`** — where the app could be attacked and what could go wrong:
   - Assets worth protecting, entry points (login, sign-up, file uploads, Edge Functions, Google integrations, chat, email inbox, web build), and trust boundaries.
   - Threats for each, using STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege), for example: one enterprise seeing another's documents, a consultant accessing admin functions, stolen Google tokens, malicious file uploads, leaked keys, account takeover, cross-site scripting on the web build.
   - For each threat: likelihood, impact, current protection, and any gap with a planned fix.

5. **`SECURITY_CHECKLIST.md`** — a pre-launch checklist that turns the four documents above into checks that can be run and ticked off, e.g. "RLS enabled on every table", "no secrets found by a repository search", "consultant account cannot open another enterprise's document via its direct link", "signed links expire", "MFA enforced for admins", "session times out after inactivity", "deletion request removes data from all tables and buckets". Each check says how to verify it (a test, a query, a manual step) and where its result is recorded. Run it once now and record the results.

**Make future work follow these documents:** create or update `CLAUDE.md` (and `AGENTS.md` if the project uses Codex) in the project root with a short section telling any AI assistant to read `docs/security/` before making changes and to update the relevant document whenever a change affects security, authentication or data handling.

**Fixing contradictions:** while writing the documents, list every place where the current app breaks a rule in them (e.g. a table without RLS, a secret in the code, a public bucket, a missing permission check, sensitive data in logs). Fix each one without changing the app's features or user-facing behaviour. If a fix *would* change behaviour, do not apply it; list it in the report for my decision. Then continue with the sections below, which must also follow these documents.

## 0b. Security hardening and full audit

After the documents in Section 0 exist, check and harden every item below. Same rule as Section 0: fix anything that is insecure without changing features; anything that would change behaviour goes in the report for my decision. For every item, record what you checked, what you found and what you fixed, and add a matching check to `SECURITY_CHECKLIST.md`.

1. **API keys and environment variables** — search the code, config files, `pubspec.yaml`, web `index.html`, Android files and build scripts for keys and secrets. Only the Supabase URL and anon key may be in the client. Everything else (service role key, Google client secrets, email credentials) moves to Supabase secrets / Edge Function environment variables. Make sure `.env` files are in `.gitignore`, add a `.env.example` with placeholder values only, and confirm no secret is printed in logs.
2. **Git history** — scan the full Git history for leaked secrets (e.g. with `gitleaks` or `trufflehog`). If any real secret was ever committed, **rotate it** (create a new key and revoke the old one) — deleting it from history alone is not enough. List every leak found and which keys I must rotate in the Supabase and Google dashboards.
3. **Authentication** — confirm every screen except login, sign-up, password reset and the public legal pages requires a signed-in user. Use Supabase Authentication only; passwords are hashed by Supabase (bcrypt), so confirm the app never stores, logs or sends passwords anywhere itself.
4. **Admin routes and access control** — protect admin and owner screens in the app's router, **and** enforce the same rules on the server side: RLS policies, Edge Function role checks and storage policies. Hiding a button is not protection. Test that each role cannot reach data or actions outside its permissions, including through direct links and direct API calls with that role's token.
5. **Database** — RLS enabled on every table with least-privilege policies; no table or view readable by anonymous users unless intended; review database functions marked `SECURITY DEFINER`; storage buckets private; run the Supabase security advisor (database linter) and fix its warnings.
6. **Forms and Cross-Site Scripting (XSS)** — validate every form on the client for usability and on the server (database constraints, Edge Function checks) for security. Never render user-supplied content as raw HyperText Markup Language (HTML) on the web build; escape chat messages, success stories, document names and email content shown in the app; validate uploaded file types by content, not just extension.
7. **API endpoints (Edge Functions)** — every function verifies the caller's token and role before doing anything, validates its input, returns generic error messages, and never exposes the service role key in a response.
8. **Rate limiting** — check Supabase Authentication rate limits (login, sign-up, password reset, one-time codes) are set sensibly; add rate limiting to Edge Functions that send emails, create meetings or call Google, so they cannot be spammed.
9. **Cross-Origin Resource Sharing (CORS)** — Edge Functions must allow only the app's real web domain(s) (and localhost in development), not `*`. Check the allowed redirect URLs in Supabase Authentication and the Google Cloud Console are limited to our domains.
10. **Security headers (Web build)** — configure on the web host: Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, X-Frame-Options (or frame-ancestors), Referrer-Policy and Permissions-Policy. Test that the app still works with them on.
11. **Debug mode** — production builds must be release builds (`flutter build --release`), with no debug banners, debug logging, test accounts, sample data or development endpoints. Android release builds should have `debuggable` off and use code shrinking/obfuscation.
12. **Dependencies** — run `flutter pub outdated`, update packages to current stable versions where safe (check for breaking changes and test after), and remove unused packages, files, assets and dead code.
13. **Exposed files** — check the deployed web build does not serve `.env` files, source maps, `.git` folders, backups, or test/config files; check nothing sensitive is in public storage buckets.
14. **Full audit report** — finish with a security audit report in `docs/security/AUDIT_REPORT.md`: every issue found, severity (critical / high / medium / low), whether it is fixed, how the fix was verified, and anything left for me to do manually (rotating keys, dashboard settings, hosting headers). Be explicit about anything you could not verify rather than assuming it is safe.
